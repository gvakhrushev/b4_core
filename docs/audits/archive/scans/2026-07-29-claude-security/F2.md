# F2: Peak-anchor daily sample slot can be squatted, suppressing peakC and over-levering every structural short

**Status:** no patch produced

Declined after analysis showed F2 cannot be closed inside `sampleAnchor` without reversing a documented policy decision. F2 (suppression) and the M-3 wick attack (inflation) are the same permissionless daily race seen from its two sides. Three existing pinned assertions make the rule complete and contradictory: AnchorRatchet.t.sol:218 and AuditH4M3_Anchors require that a single observation at least a day after the last counted sample MUST bind the value; test_M3_intraday_wick_cannot_move_the_confirmed_peak requires that an observation less than a day after it MUST NOT bind. Closing F2 requires that a later same-day observation at the true high MUST bind — the same on-chain event sequence as the second rule, demanding the opposite outcome. The only differing fields are msg.sender (free to create) and the elapsed time, so no witness or dwell threshold separates the cases; it only prices the wick. This is why the verifier's reproduction succeeded — its probe is the F2 attack with the roles swapped, so any patch admitting the honest high must admit the probe. Detect-and-withhold is also unavailable: with the peak withheld, shortStructLev rises to 1.726x versus 1.279x for the suppressed value, so withholding is more levered than the harm it would replace. The three ways forward are all owner policy calls: accept F2 as a residual; adopt the low side's monotone ratchet, closing F2 and accepting M-3; or change the trust model with a registered sampler set or a non-instantaneous daily close, both of which have dated precedent against them (HAZARDS G2 and section 4.15; the second-oracle dependency declined at spec/HAZARDS.md:180 C4 on 2026-07-18).

## The claim that could not be made with confidence

- **the change introduces no new security vulnerability** -- NOT_CONFIDENT: the attempt's dwell channel let two prints two hours apart move peakC 5,000 to 50,000 on an already-claimed day, promoting prevPeak identically and raising shortStructLev 0.720x to 0.961x, which base refused
- **beyond closing the finding, the change does not alter the code's behaviour or the inputs it accepts** -- NOT_CONFIDENT: any two observations at least an hour apart in a peak window moved peakC where B4Pool.sol:478 previously admitted only the daily slot, changing the value fed to every structural short

## The report's original recommendation

Decouple the value ratchet from the density counter on the peak side, mirroring the low side: let `a.peakC = max(a.peakC, pxp)` on every in-window observation, and keep `_recordDistinctSample` solely as the confirmation counter. If daily-cadence value binding must be retained to block the M-3 wick attack, take the peak from a manipulation-resistant reference (e.g. a TWAP / oracle px) rather than the instantaneous `spotPx` at a caller-chosen instant, and/or accept more than one counted observation per day so a single squatter cannot monopolise the slot. Note that the first half of this recommendation is exactly the M-3 reopening described above, so it is a risk-acceptance decision, not a drop-in fix.
