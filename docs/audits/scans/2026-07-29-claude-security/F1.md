# F1: Exit-weight forfeiture is gated on exact `keep == 0`, so `initiateExit(WAD - 1)` withdraws ~100% of a vault's capital while keeping its full reported pool weight

**Status:** no patch produced

Two attempts, both rejected. The first made forfeiture strictly proportional and repriced every ordinary partial exit — a 50% exit lost half its weight — which reverses an economic decision the repository made deliberately (docs/audits/REVIEW-2026-07-25-agent-changes.md:418-431, INVARIANTS.md:82, and the AuditHalfB docstring 'a PARTIAL exit is not a departure'). The second attempt narrowed it to a materiality floor measured on the post-exit base, but the verifier executed the exploit against the patched sources and it still worked: rewardBaseWad = (R + C*x)*keep is re-inflated by the departing capital's own profit, so with unsettled profit a vault paid out 99.2% of its holdings and kept 100% of its reported weight, splitting the basket 50/50 with a fully-invested stayer. The finding is real and remains open; closing it needs a measure the pool can verify itself rather than a caller-supplied post-exit base whose inflation term the owner controls.

## The claim that could not be made with confidence

- **beyond closing the finding, the change does not alter the code's behaviour or the inputs it accepts** -- NOT_CONFIDENT: with no unsettled profit the second attempt repriced ordinary large partial exits — 90% exit kept 84% of weight, 95% kept 42%, 99% kept 8%, all 100% at base

## The report's original recommendation

Make the forfeiture proportional rather than boundary-triggered: reduce the pool-side reported weight by the exited fraction on every exit (e.g. add a `forfeitWeightPartial(id, x)` that does `it.weightOf[msg.sender] -= wmul(w, x); it.totalWeight -= wmul(w, x);`, still confined to the pre-`reportDeadline` window and still a silent no-op on every non-applicable case so it can never revert the crank-path exit). Gating on a dust threshold instead of `keep == 0` only moves the boundary and remains gameable. Note the verifier's added constraint: derive the retained claim from state the pool can verify, or from a base measured before the `clientShare * x` credit, since the post-exit base is owner-influenced.
